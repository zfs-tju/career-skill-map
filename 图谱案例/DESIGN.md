# WorkWill 技术设计文档

> agent2026-WorkWill · 天津大学"实事求智·创见未来"AI智能体大赛 · 技术实现赛道

## 一、系统概述

WorkWill 是一个"文档 → 知识图谱 → 职业规划决策"的端到端系统：用户以四通道导入就业相关材料，多智能体流水线将材料抽取入图，前端以 ECharts 力导向图呈现四大维度图谱，并提供**个性培养 / 职业方向**两大智能报告、检索溯源与个人画像。

### 1.1 总体架构

```text
┌───────────────────────────────────────────────────────────────┐
│ 展示层  index.html + main.js（原生JS，4400行）                  │
│   ECharts 力导向图谱（四大维度）/ 报告面板 / 时间轴画布 / 我的画像 │
├───────────────────────────────────────────────────────────────┤
│ 服务层  app.py（Flask，37 个 API 路由）                         │
│   ├── 导入编排：通道A网页 / B文本 / C图片OCR / D Excel 四通道    │
│   ├── 图谱读写：节点/边 CRUD、重导入、全局重建                  │
│   └── 报告引擎：模式判定 detect_report_mode                     │
│        ├─ M4 个性培养：四段式 + mindmap 培养思维导图            │
│        └─ M5 职业方向：四段式 + career_paths 多路径图           │
├───────────────────────────────────────────────────────────────┤
│ 智能体层  天津大学校内词元服务 ai.tju.edu.cn（tju-llm）         │
│   抽取引擎 · JSON修复器 · 文本校对器                            │
│   维度分析框架 · M4/M5 报告专家                                 │
│   岗位总览 / 九段路径 / 学年规划 / 条目解读 等专职角色           │
├───────────────────────────────────────────────────────────────┤
│ 数据层  db.py（SQLite 三库分置）                                │
│   工作区库 × N │ 全局聚合库 │ 账号库                           │
│   本地OCR：RapidOCR（ONNX Runtime，懒加载）                    │
└───────────────────────────────────────────────────────────────┘
```

### 1.2 技术选型理由

| 选型 | 理由 |
| --- | --- |
| Flask + SQLite | 单机零运维，双击即可在校园电脑运行 |
| RapidOCR（本地） | 截图导入不依赖外部服务，离线可用 |
| openpyxl | 直接读写培养方案与六表 Excel |
| 天大校内词元服务 | 比赛指定基础设施；OpenAI 兼容 chat/completions 接口，切换模型零成本 |
| 原生 JS + ECharts | 无构建链，前端零编译；力导向图天然适合节点-边交互 |

## 二、数据模型

### 2.1 三库分置（db.py）

| 库 | 位置 | 职责 |
| --- | --- | --- |
| 工作区库 | 每个材料文件夹一个 | 保存该工作区原始抽取结果 |
| 全局聚合库 | `data/db/graphs/` | 跨工作区合并视图，支撑综合分析与报告 |
| 账号库 | `data/db/accounts/` | 用户与个人画像（技能点亮、个性培养布局） |

### 2.2 核心表结构

**nodes**：`id`(TEXT PK)、`name`、`type`、`category`、`properties`(JSON)；全局库带 `source_folders`。
**edges**：`source`、`target`、`relation`、`label`、`support`(证据)、`page`(页号溯源)、`product`、`attrs`(JSON)、`source_level`；旧库通过 `PRAGMA table_info` 检测自动重建迁移。
**users**：`username`(UNIQUE)、`salt`、`password_hash`（加盐哈希）、`created_at`。

### 2.3 全局合并策略（sync_folder_to_global）

同类型同名节点合并（属性并集、`source_folders` 记录全部来源）；边按 `source + target + relation` 去重。

### 2.4 图谱维度与六表契约

**界面呈现四大维度**（侧边栏图谱维度菜单）：

| 维度 | 英文 key | 副标题 |
| --- | --- | --- |
| 专业岗位 | job_cluster | 本专业常见岗位 |
| 技能结构 | skill_structure | 岗位技能要求与分类分级 |
| 课程体系 | course_system | 专业课程培养与技能对接 |
| 竞赛实践 | competition_practice | 竞赛锻炼技能与面向专业 |

**底层数据契约仍为六表**：发展路径（career_path）、岗位竞合（job_coopetition）两表数据持续入库，作为智能报告的取数底座，不在图谱菜单单独呈现。六表列契约：

| 表 | 列契约 |
| --- | --- |
| 岗位聚集 | 岗位名称、岗位类别、需求年份、招聘企业、企业所在城市、行业领域、薪资范围、数据来源、页号 |
| 技能结构 | 岗位名称、岗位级别、核心技能、技能分类、技能等级要求、工具/平台、认证证书、技能描述、学习难度、替代技能、数据来源、页号 |
| 发展路径 | 起始岗位、起始职级、目标岗位、目标职级、所需新增技能、转换难度、平均年限、职业方向、数据来源、页号 |
| 课程体系 | 专业名称、学科门类、课程名称、课程性质、开课学年、开课学期、核心知识点、培养技能、开设学院、数据来源、页号、学分 |
| 岗位竞合 | 岗位A、技能组A、岗位A描述、技能重叠度、岗位B、技能组B、岗位B描述、数据来源、页号 |
| 竞赛实践 | 竞赛名称、竞赛级别、主办单位、时间节点、面向专业、锻炼技能、竞赛描述、数据来源、页号 |

每一行强制携带"数据来源 + 页号"——这是全系统溯源与接地能力的根基。

## 三、多智能体协同设计（核心）

系统不把大模型当作单一"黑盒问答机"，而是拆分为职责单一、可校验的专职智能体，全部经由天大校内词元服务调用。

### 3.1 智能体角色表

| 智能体 | 职责 | 关键约束 |
| --- | --- | --- |
| **抽取引擎** | 从材料中抽取结构化六表 JSON | 严格按六表契约输出；"宁空勿滥"——文档里没有的维度输出空数组 |
| **JSON 修复器** | 修复非法/被截断的 JSON | 只输出修复后的纯 JSON |
| **文本校对器** | 删除报告中图谱不存在的实体句 | 防幻觉出口回路 |
| **维度分析框架** | 为每个维度定义分析专家视角与核心问题（DIM_ANALYSIS_PROMPT） | 报告生成的分析骨架 |
| **M4 个性培养报告专家** | 四段式培养路径报告 + mindmap 培养思维导图 | 学期归位铁律（见 4.2） |
| **M5 职业方向报告专家** | 四段式 + career_paths 多路径方向图 | 路径类型与节点逐字约束（见 4.3） |
| **就业总览专家** | 按专业生成岗位分类总览（图二） | 供学生总览就业面 |
| **路径规划专家** | 九段式职业发展路径图（图三） | 段落结构固定，右侧工具栏联动 |
| **学年规划导师** | 分学年时间准备规划（plan_detail） | 面向"专业 + 目标路径" |
| **智能分析顾问** | 课程/竞赛/技能/岗位条目简明解读 | 服务图谱点击场景 |

### 3.2 文档类型感知抽取（DOC_TYPE_TEMPLATES）

导入时先对文档判型，再挂载对应抽取模板，内置 5 套：**职业标准类 / 培养方案类 / 政策·行业报告类 / 竞赛认证类 / 自动识别**。每套包含：

- `dim_hints`：各维度抽取提示（如职业标准类只抽岗位聚集+技能结构，职级按"五级/初级工→高级技师"映射）；
- `extra_rules`：领域规则（如"适用专业：xxx"追加格式）；
- `forbidden`：明确禁抽清单。

**禁抽机制是控制幻觉的第一道闸门**。

### 3.3 抽取流水线

```text
材料输入 → 文档判型 → 挂载模板 Prompt → 抽取引擎(六表JSON)
        → 失败/截断 → JSON修复器 → 结构校验
        → 落盘工作区库 → 同步全局聚合库(合并去重)
```

长文档按 `WEB_EXTRACT_MAX_CHARS = 30000` 字符分段，逐段抽取后合并。

## 四、智能分析报告体系（核心）

### 4.1 模式判定（detect_report_mode）

报告模式收敛为两种，自动判定规则：**搜索对象是岗位 → M5 职业方向；专业/技能/其他 → M4 个性培养**。历史模式 m1 岗位对标 / m2 专业出口 / m3 技能评估保留兼容映射（m1→m5，m2/m3→m4），UI 仅提供 M4/M5 两个选项。

### 4.2 M4 个性培养报告——"我这个专业四年怎么走"

**输出结构**：四段式报告（title / summary / target_profile / four_year_plan / action_list / table / gap_next）+ 顶层附加字段 **mindmap（个性化培养思维导图）**。

**mindmap 五大分支**（顺序固定）：大类通识课 → 专业必修课 → 专业选修课 → 选修课 → 竞赛实践；每分支按"大一~大四"逐年列出条目。

**学期归位铁律**：
- 课程只按节点属性"开课学年 / 开课学期"归位，学期括注格式"（大二·秋）"；
- 开课学期为逗号多值（如"秋,春"）表示两学期都开，逐值括注；
- **禁止猜测学期、禁止把课程默认堆到同一学期、禁止编造课程凑数**。

**目标岗位叠加**：用户给定目标岗位时，专业选修课分支必须从数据中真实存在的选修课里给出"★建议优先"标记与一句话选课策略（recommend_note），禁止编造不存在的课程名。

**竞赛实践分支保底**：数据中的竞赛/实践节点优先采用；四年合计不足 4 条时用该专业广为人知的竞赛建议补足，逐条尾注"（AI建议）"。

### 4.3 M5 职业方向报告——"毕业时我能走哪几条路"

**输出结构**：四段式 + 顶层附加字段 **career_paths（职业方向路径图）**。

**路径覆盖**：5-8 条，类型覆盖就业（1-3 条，岗位名逐字取自图谱相邻岗位）、考研 / 升学读研 / 直博、选调 / 支教保研 / 干部保研等政策路径；与专业明显无关的路径省略。

**每条路径**：
- `path_nodes`：3-6 个按成长先后排序的关键节点（type 限技能/课程/竞赛，name 逐字来自图谱节点，带来源），渲染成"专业 → 课程/技能/竞赛 → 目标"发散导图分支；
- `steps`：4-8 步分学期时序动作（"大二·春"式），就业路径步骤须落到图谱真实节点并标注来源；
- `advice`：1-3 条专属建议，禁止"要努力学习"式空话。

**岗位联动**：点击报告中的具体岗位，右侧固定工具栏展示**九段式职业发展图**（career_detail），配合岗位分类总览（career_overview）形成"总览就业面 → 选方向 → 看单岗发展"的完整动线。

### 4.4 分层接地规则（GROUNDING_RULES，防幻觉核心）

| 层 | 规则 |
| --- | --- |
| **事实条目** | target_profile 全部条目及 four_year_plan/action_list 中 tag=course/skill/comp 的条目，只能基于送入的子图数据，句尾标注 `[来源：数据来源名 页号]`（来源逐字取自关联关系字段）；图谱未覆盖的事实保持沉默，交给 AI 建议层 |
| **AI 建议** | tag=advice 条目、timepoints、pitfalls、top3、alternatives：开放生成、无需来源标注；可写真实广为人知的竞赛/证书/工具名（电赛、蓝桥杯、LeetCode…），但**禁止编造具体企业名**（统一"行业头部企业"）与**具体薪资/比例数字** |
| **三层来源分级** | 官方培养方案/国家职业标准 = **权威层**；其他文档来源 = **多源抽取层**；AI 建议 = **建议层**；三者由渲染层自动分级标注，不得混排 |

### 4.5 我的画像与个性培养布局

账号体系下，个人技能档案支持"技能点亮"；**个性培养布局编辑器**与 M4 报告画布同款数据结构，用户可在画像中直接编辑课程/竞赛的类目归属与时间轴位置并保存，报告按此布局展示——用户从"报告读者"升级为"布局共同编辑者"。

## 五、四通道导入设计

| 通道 | 路由 | 流程 |
| --- | --- | --- |
| A · 网页URL抓取 | `POST /api/import_url` | 抓取网页正文 → 抽取流水线 |
| B · 粘贴文本 | `POST /api/import_text` | 文本（≤30000字符/段）→ 抽取流水线 |
| C · 图片OCR | `POST /api/import_image` | RapidOCR 本地识别 → 行聚类还原版面（y 中心相近归一行、行内按 x 排序）→ 抽取流水线 |
| D · 培养方案/Excel直传 | `POST /api/upload` | 标准六表直接入库；检测到培养方案工作簿则经 `_is_training_plan_workbook → _convert_training_plan → _ensure_training_plan_standard` 自动转换 |

四通道统一经 `POST /api/import_confirm` 确认落盘。前端引导语按场景分流："JS 动态页面用通道 B 粘贴正文；培养方案 Excel 用通道 D 直传（不走 OCR）；文字截图用通道 C"。

## 七、关键工程细节

1. **OCR 懒加载单例**：RapidOCR 首次调用时初始化全局单例，避免服务启动阻塞；未安装该依赖时仅通道 C 降级。
2. **边表平滑迁移**：旧库缺列时通过 `PRAGMA table_info` 检测并自动重建迁移。
3. **年级感知报告**：报告生成支持叠加用户年级，M4 培养路径只覆盖"当前学年 → 大四"，不再生成已错过的低年级学期。
4. **一键启动与 venv 自愈**：按命令行特征 + 端口双重清理残留进程 → 启动前对 venv 做两级自检（解释器可运行 + 核心依赖可导入；venv 的 `pyvenv.cfg` 硬编码创建时的解释器绝对路径，拷贝到别的机器或移动项目目录都会失效）→ 失效则自动删除重建并重装依赖 → curl 探活成功后自动打开浏览器。
5. **限速合规**：所有 LLM 调用集中走统一端点函数，可控频次，符合平台 60 次/分、3000 次/时限制。
6. **安全**：密码加盐哈希存储；账号库与图谱库物理分离；溯源信息（来源+页号）只增不改。
7. **PDF 原件溯源定位**：扫描 `data/raw / extracted / graphs` 建立"归一化来源名 → 本地原件"进程内索引（`_build_source_file_index()`），`GET /api/source_file` 按来源名在服务端允许目录内检索原件；前端溯源面板打开 PDF 时追加 `#page=页号` 直接跳到被引用页，与六表强制携带的"数据来源 + 页号"构成"抽取 → 引用 → 回跳原件"的完整闭环。
8. **图谱交互（四大中心视图 + 多级关联）**：默认布局为 hub"四大中心"探索视图——四大维度各成一个中心锚点，维度内结构辐条常显，**跨维度真实关系边基态隐藏**；悬停中心锚点（`buildAnchorFocus`：该中心全部成员对其他中心的关联）或成员节点（`buildNodeFocus`：该节点参与的跨维度边）时动态淡入点亮关联线，移出即收起（防抖调度 + tooltip 提示"悬停查看跨中心关联"，信息按需触发不过载）。检索侧 `_build_subgraph()` 以匹配节点为种子做 BFS 多跳扩展（level 0 → N 跳，二跳以上邻居受 `MAX_FANOUT` 上限约束），`depth` 参数 1-3 层可调（种子实体搜索 1-4 层、默认 3），前端实时提示"匹配 N 个节点（展开 depth 层）"；同名同类型节点按全局 ID 规范 `类型:名称` 跨维度自动合并，保证多级关联跨维度时指向同一实体。

## 八、运行与部署

- 环境：Windows + Python 3.10+；依赖仅 `flask / openpyxl / requests`（OCR 按需，通道 C 首次使用前手动安装 RapidOCR）。
- 启动：双击 `一键启动.bat`（含 venv 失效自检与自动重建，拷贝文件夹到其它电脑 / 移动项目路径后均可直接双击），或 `pip install -r requirements.txt && python app.py`。
- API Key（合规要求，不入库）：启动时按 `环境变量 TUJU_API_KEY` → 根目录 `api_key.txt`（已被 `.gitignore` 排除）两级读取校园 LLM Key，见 `app.py` 的 `_load_llm_key()`；未配置时服务照常启动，仅大模型相关功能（材料抽取 / 智能报告 / 智能解读）不可用，图谱浏览等基础功能不受影响。
- 访问：<http://127.0.0.1:6006>。
- 数据：`data/` 目录运行时自建，包含工作区材料、三库 SQLite 与导入缓存。
